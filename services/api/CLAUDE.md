# api — service-specific rules

NestJS backend: REST + Socket.IO gateway + dispatch engine. Read the root `CLAUDE.md` first.

- Vertical slices under `src/features/<name>/` (auth, users, drivers, rides, dispatch, pricing, payments, ledger, geo, geozones, notifications, support, stats). Each slice: `<name>.module.ts`, controller, service, schemas (zod from `@taxi/shared` where cross-surface), tests.
- **Vehicles are not a slice of their own** — they live inside `features/drivers/`. A vehicle belongs to a driver (`vehicles.driver_id` FKs `drivers.user_id`), and splitting them would force a cross-slice import for the child-seat/category filters dispatch runs.
- `vehicles.plate` is unique platform-wide, on `upper(plate)` (migration `0004`) — it is the identity a rider matches at the kerb. A collision is a 409 `plate_taken` on every write path, never a raw constraint 500.
- Ride status writes ONLY via `RideTransitionService` (`features/rides/ride-transition.service.ts`), which is the one caller of `assertTransition()` and the one writer of `rides.status`. Two consumers: dispatch and the ride lifecycle. Money ONLY in integer cents.
- A ride is **created** at an entry status (`features/rides/ride-entry.ts`) — creation is the machine's entry, not a transition, because `assertTransition` needs a `from`. Every status change after that goes through `RideTransitionService`; everything from `accepted` onward lives in the `features/rides/lifecycle/` sub-slice (the driver's four steps, all four cancellation branches, the payment-method lock, the settled split). The ride ends at `settled`: `features/payments` takes `completed → settled` on `POST /rides/:rideId/settle`, and that transition IS the settlement lock — settling is idempotent, so an already-settled ride and a lost race both answer with the settled ride (201, like `complete`), never a 409.
- **`features/ledger` is the only writer of `ledger_entries` and of `drivers.balance_cents` as money.** Every settlement posts a balanced six-entry set sharing one `transaction_id` — the fare, the commission, and the collection (who physically took the passenger's money: the driver on cash, the platform on card). Card and cash differ in exactly that one pair, every party's account is a **balance** (a rider nets to zero on both methods), and the platform account is a **contra** account — read it by entry type, never as an aggregate. The balance moves only as `balance_cents + delta` (a `sql` fragment), never read-modify-write.
- **Payments: the charge happens BEFORE and OUTSIDE the transaction**, for the same reason as the socket-emit rule — a provider call cannot be rolled back. The Stripe idempotency key is **derived from the ride** (`settle:<rideId>`), never per attempt: that is what makes "charge succeeded, database rolled back" survivable. Cash never calls the provider at all, which is why the branch sits above the seam. **Commission is never recomputed at settlement** — the split is read from the columns #11 wrote and re-parsed through `fareSplitSchema`.
- Dispatch drops a driver only at `balanceCents < -driver_debt_limit_cents` (`platform_config`, €50 seeded), never at zero — a cash-only driver is permanently negative by design, and a hard zero would strand them after one ride. The limit travels on `DispatchContext`; strategies never read config themselves.
- The **settled split is COPIED** from the accepted `ride_offers` row's `split` snapshot, never recomputed. `buildOffer` resolves the commission per driver, so re-resolving at completion would pay a driver a number different from the card they accepted — the €200→€130 grievance, in our own codebase.
- **No socket emit inside a database transaction.** `RideTransitionService` is split into `transitionInTx` (composable, no emit) and `emitStatus` (post-commit) precisely so this cannot happen: Socket.IO has no rollback, and a `ride:assigned` that reached a phone before a rollback is worse than the 409 it replaced. `rides.driver_id` is written only by `RidesRepository.assignDriver`, which also stamps `rides.vehicle_id` (#86).
- **The dispatch engine never imports a concrete strategy.** `DispatchService` reaches `auto_match`/`geozone_queue` only through `DispatchStrategyResolver`; mode is per geozone, falling back to `platform_config.default_dispatch_mode`. Dispatcher force-assign is a privileged command, not a strategy.
- **Geozone precedence: the smallest containing polygon wins** (`features/geozones`). Vecrīga is deliberately nested inside centre and autoosta overlaps both, so the lookup is `ST_Contains(polygon, point) ORDER BY ST_Area(polygon)` in SQL — polygons are never read into JS. `ST_MakePoint(lng, lat)` takes longitude first.
- Dispatch is a **background process**, not a request handler: a polling `DispatchSweeper.tick()` drives it, and every piece of cascade state is a `ride_offers` row rather than a timer, so a restart strands nothing. The sweeper does not auto-start under `NODE_ENV=test` — specs call `tick()` themselves.
- Maps go through **two** `CachingMapsProvider` facades over **one** `MAPS_PROVIDER_SOURCE` (`features/geo`): `MAPS_PROVIDER` (`quote`, 24 h TTL, pricing) and `MAPS_PROVIDER_ETA` (`eta`, 5 min TTL, the tracking page). Two, because the consumers read different fields with different staleness tolerances — pricing `distanceMeters`, tracking `durationSeconds`, which is what traffic moves — and separate key namespaces make that TTL split structural rather than a convention. Tests override the **source**, so both stay under test and one counter still sees every paid call — that count assertion is the `<€100/mo` guardrail. `StubMapsProvider` throws at boot under `NODE_ENV=production`, like `SMS_PROVIDER`.
- A provider's free-text `error.message` **never reaches a log line or a Redis value**. `geo.maps.route_failed` carries a closed-enum `reason` and a `cell` hash of the cache key instead, which is what makes "no coordinate in a log" structural rather than dependent on a scrubber a future provider's message format could slip past. The negative cache is **on for `eta`, off for `quote`** — poll amplification is the tracking page's problem, and a cached failure on the booking path would block real bookings; say which caller whenever you state what it bounds.
- A rejected **cache entry is recoverable, not fatal**: delete it and re-fetch. Parse on write too, so a bad value never lands. Throwing on the read instead pins that corridor to a 500 for the whole TTL, and the busiest routes are the ones that cached.
- Paid-call spend is bounded from both ends: the cache covers ordinary traffic, and a per-rider cap (`features/rides/rides.policy.ts`) covers the hostile case — a caller varying coordinates by >~11 m misses the cache every time. A new ride-creating path needs both.
- Fares come from `ride_tariffs` rows (per city × category) and the commission from `platform_config`, both read at quote time — **no rate or percentage is ever a literal in code**.
- `POST /rides` takes the rider id from the JWT; `rideRequestBodySchema` has no `riderId` field, by construction.
- `POST /rides` **requires** an `Idempotency-Key` header (`IDEMPOTENCY_KEY_HEADER` in `@taxi/shared`, a uuid per booking attempt). The rider-scoped reservation is atomic (`setIfAbsent`), released on failure, and replays out of Postgres — a new ride-creating path needs the same.
- Provider SDKs (Google Maps, Twilio, Stripe) are imported ONLY inside the slice implementing the corresponding seam interface from `@taxi/shared/seams`; everything else injects the interface.
- A dev-only seam stub must THROW at boot under `NODE_ENV=production` rather than serve silently — see the `SMS_PROVIDER` factory in `features/auth/auth.module.ts`. Secrets are validated the same way: production refuses the values committed to `.env.example` and anything too short (`common/config/env.schema.ts`), so a new secret belongs in that check.
- Live driver locations live in Redis (GEO sets); PostGIS/Drizzle for persistent data (geozones, recorded tracks). Drizzle migrations in `db/`.
- Live positions go through `DRIVER_LOCATION_STORE` (a Redis GEO port in the drivers slice). **The location ping path must never reach `DRIZZLE`** — presence lives in the Redis online set precisely so it doesn't have to, and a spec boots that path with a `DRIZZLE` provider that throws on any access. The gateway's `handleDisconnect` is a different path and deliberately does write Postgres, so the rule is about the ping, not the class.
- `drivers.status = 'on_ride'` is written only by the ride lifecycle — `RideLifecycleService.claimDriver` (which dispatch composes into its accept and force-assign transactions) and the release inside `complete`/`cancel`. Both are conditional UPDATEs whose `false` is ordinary, never an error: a force-assigned OFFLINE driver is never claimed and never released. The driver-facing presence route accepts `online`/`offline` only (`DRIVER_PRESENCE_STATUSES`). Going online is additionally refused (409 `driver_on_ride`) while the driver has a ride in `ACTIVE_DRIVER_RIDE_STATUSES` — the rides table decides, not `drivers.status` (#61).
- Socket event names/payloads come from `RT` in `@taxi/shared` — never string literals.
- Cross-cutting Nest plumbing (env config, Drizzle, Redis KV, the zod pipe) lives in `src/common/`; `src/features/` stays feature-vertical.
- Auth is fail-closed: `JwtAuthGuard` + `RolesGuard` are global (`APP_GUARD`); a route is only reachable unauthenticated with `@Public()`. Sockets authenticate in the handshake, and clients never request room joins.
- Logging: structured, `domain.component.action_state` taxonomy (see `.claude/references/logging-standard.md`).
