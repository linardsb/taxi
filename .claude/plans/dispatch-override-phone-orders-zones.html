#19 — Dispatch console: override, phone orders, zones

What we're building, and why

#18 gave Dina a board she can watch. #19 makes it a board she can act on: take a booking call and create the ride, see who the algorithm is offering it to and why, and put a different car on it when she knows better.

It matters because the phone channel is half the product thesis. "Can both call and use the app" is riders' #2 reason to switch (S10-3), and Dina — who ran planning at Lady Taxi — is the differentiator Bolt structurally can't match and Panda can't staff. Right now there is literally no way to book a ride by phone: POST /rides is @Roles('rider'), rider-self only.

The five concepts this plan rests on

1 · Two assignment verbs, and one guarded state machine

Every shipped dispatch product splits assignment into two verbs. Offer asks a driver — they may accept or decline inside a timer. Force-assign tells them — no accept step, the driver is simply notified. Onro and Onde both ship exactly this pair, independently.

In our code both are just walks through ALLOWED_TRANSITIONS, the one guarded state machine in the repo. requested → accepted is illegal, so ForceAssignService walks the ride requested → offered → accepted, writing an already-accepted offer row on the way. That second hop is the real guard: a ride that already moved on fails there with a 409 instead of being forced. 

requested ──offer──> offered ──accept──> accepted ──> arriving ──> arrived ──> in_progress
    ^                    │                    │
    └──decline/timeout───┘                    │
    └───────────── #19 adds this ─────────────┘   (dispatcher release, for reassign)

Why this plan needs it: reassigning an already accepted ride has no legal path today — the only exit is cancellation, which kills the rider's ride, tracking token and SMS thread. Phase A adds one transition (accepted|arriving → requested) so a reassign is a release back into the cascade. It's a cross-surface contract change, which is why it's Open Question Q2 rather than a quiet edit.

Where the ticket and the code disagree. #19's failure-case AC says assigning a just-went-offline driver should give "a clear error + re-offer". #10 deliberately built the opposite: force-assign bypasses eligibility entirely, because overriding onto an offline driver is the feature — Dina has Jānis on the phone, his app crashed, she still needs to send him. Resolution: the console warns and asks for a second confirm; the API is unchanged; the 409 (ride already moved on) is the real error, and the cascade resuming is the "re-offer".

2 · Autocomplete session tokens — why address search is free at pilot volume

Google bills address typeahead per keystroke, which is terrifying until you know about session tokens. A session is one user finding one address: you mint a token, send it with every keystroke request, and send it once more with the final "give me the coordinates" call. Google then bills the group as one unit rather than as n independent requests. 

mint token ──┐
             ├─ "Brīv"        ─┐
             ├─ "Brīvības"     ├─ Autocomplete (New)   $2.83 / 1,000
             ├─ "Brīvības ie"  ─┘
             └─ resolve placeId ─ Place Details Essentials  $5.00 / 1,000
                                  ↑ TERMINATES the session

Free tier: 10,000 calls per SKU per month (Essentials)

At the PRD's month-3 target — 100 rides/week, worst case all of them phone-booked, 2 address fields each, ~5 debounced keystrokes reaching the API per field — that's 4,330 autocomplete calls and 866 details calls per month. Both sit inside the free 10,000-per-SKU allowance, so the expected cost is €0.

Where the analogy breaks: a token doesn't make requests free, it makes them groupable — and only if the session terminates with the right SKU. Terminating with Place Details Essentials (IDs Only), which sounds cheaper because it's $0, actually voids the session and bills every keystroke individually. That single wrong field mask is the difference between €0 and a real bill.

Why this plan needs it: StubMapsProvider.geocode() throws today and the seam has no autocomplete method at all — there is no way to turn "Brīvības iela 45" into a bookable point. Everything downstream (quote, ETA, zone, auto-match) needs coordinates, because addressPointSchema requires a location.

3 · Seams — why a stub is a real deliverable

A seam is an interface in packages/shared/src/seams/ that every call site goes through, so the thing behind it can be swapped without touching the callers. sms-provider.ts is nine lines and no implementation; that's the shape. 

packages/shared/src/seams/
├── maps-provider.ts        ← #19 adds searchAddress() + resolvePlace()
├── sms-provider.ts         ← the shape to copy
└── telephony-provider.ts   ← #19 CREATES this (the architecture's named gap)
                               dial() · currentCaller()
                               bound to a stub; SIP screen-pop lands later,
                               same UI either way

Why this plan needs it: the evidence is unambiguous that SIP screen-pop can wait (week-2+, not day-1) but that caller-ID prefill cannot — it's the one phone feature with measured savings, 15–45 s per call. The seam is what makes those two statements compatible: Dina types the number today, a gateway supplies it later, and the console code doesn't change.

4 · Alarm discipline — status is not an alarm

ISA-18.2 and EEMUA 191 came out of Piper Alpha and give hard numbers: an operator processes about one alarm a minute; more than ten in ten minutes is a flood; a well-managed console averages under six an hour. The rationalization rule is one sentence — an alarm exists only if it requires an operator response. 

ALARM  (toast · flash · beep)      STATUS  (recolor in place)
  dispatch:unclaimed                 ride accepted / arriving / arrived
  dispatch:sms_failed                cascade countdown ticking
  socket went offline                queue positions changing
                                     assign succeeded
  ── budget: < 6 / hour ──

Why this plan needs it: everything #19 adds is on the right-hand column, and the single most natural thing to build is a cheerful "ride assigned!" toast. That toast is the regression. Dina left a console that "often freezes" and a wall of blinking; calm is the feature.

5 · One explanation string, shared by two audiences

Every auto-pick answers "why this driver" in one line: «Āgenskalns rinda #1 · zonā 47 min · 4 min attālumā». Dispatchers override confidently only when they can see the logic; drivers, per the transparency research, want the same explanation after the fact. 

packages/shared/dispatch-explanation.ts
        explainAssignment({ strategy, zoneName, queuePosition,
                            secondsInZone, etaSeconds })
                     │
        ┌────────────┴────────────┐
   Dina's console            Driver app (#15)
   (cascade strip)           (why you got it / didn't)
        └──── byte-identical ────┘

Why this plan needs it: the identity is the whole mechanism. It turns "why did Jānis get that job?" from a phone argument into a self-service answer — S7-2 fairness, Dina's top carry-over from the autoosta. If it ever gets composed twice, the feature quietly stops working while every test stays green.

The plan at a glance

Phase A — Override

Force-assign UI, driver picker incl. offline drivers, reassign, cancel. One state-machine row added.

Phase B — Phone orders

Dispatcher booking endpoint, customers + venues, Places typeahead, telephony seam, keyboard-first form.

Phase C — Zones

Queue snapshot + join times, zone grid, cascade strip, the shared explanation string.

The three phases are independent — none blocks another, each ends on its own green gate. Recommended execution is three PRs. Phase D is acceptance closure: the AC scenarios as integration tests, the phone-share query, and the ledger rows measured.

Both open decisions closed 2026-08-17. Q2 — ratified: release, not reassign-as-cancel. The tracking token is minted once per ride and #17 reuses it, so cancel-and-rebook takes the rider's live link away at the moment their car changes; "searching" is the smaller loss, and the tracking page already maps requested → searching. Blast radius re-derived, not inherited: apps/rider and apps/driver have no src/ yet. Two forward-only assumptions the transition breaks are decided in the plan — the payment-method lock re-opens during the release window (kept, nothing is written to the ledger at accepted), and onStatus's "at most once per ride" premise is now false, which is the stated reason there is no dedupe table (follow-up A15: rewrite that argument).
