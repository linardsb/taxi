Spike #4 — the iOS field run, in five minutes

Plan: .claude/plans/spike-gps-field-test-ios-run.md · issue #4 · gates #14

What we're building and why

Nothing ships to users. We put the existing GPS harness on your iPhone, drive around Rīga for 30–45 minutes with the screen locked, and let analyze.mjs turn the recorded fixes into a PASS / FAIL / INCONCLUSIVE verdict. That verdict decides how #14 (the driver app's location slice) is built: background streaming as designed, or the free mounted-phone pattern.

The Android run on Atis's phone was the original decisive run; it isn't available. So the plan measures what it can (iOS), says plainly what it didn't (Android), and picks a safe default for the unmeasured half.

The concepts this plan rests on

1. How iOS lets an app keep the GPS on in the background

Three things must all be true: the app declares UIBackgroundModes: ["location"] in its Info.plist (a build-time promise), the user grants Always location (not "While Using"), and the app keeps a location session running when it goes to the background. Miss any one and iOS suspends the app the moment the screen locks.

Info.plist: UIBackgroundModes = [location]      ← already in app.json
   + user: "Change to Always Allow"             ← one-shot prompt, Task 1.3
   + startLocationUpdatesAsync(...) still running
   = fixes keep arriving with the screen locked

user force-quits (swipe away)  →  updates stop until the app is opened again

Analogy: a night-shift pass. The building (iOS) issues the pass at build time, the guard (the user) has to stamp it "Always", and you must actually be at your desk when the lights go out. Where it breaks: if you leave the building (force-quit), the pass doesn't get you back in — someone has to open the door (relaunch). That's why the plan has a separate force-quit check and why #14 carries a "you've gone offline" nudge.

The Always prompt appears once. "Keep Only While Using" can't be undone from inside the app — only in Settings → Privacy & Security → Location Services → GPS Spike. Precise Location must also be on, or BestForNavigation isn't even available.

2. Free signing: the Personal Team

Apple will let a free Apple ID sign an app for your own phone. Xcode creates a "Personal Team" and a certificate; the CLI (expo run:ios --device) registers the phone and builds a profile. The catch is expiry: the profile lasts 7 days, so the build has to happen within a week of the drive. The phone also needs Developer Mode on (iOS 16+) and a one-time "trust this developer".

Mac (Xcode 26.3, your Apple ID)  ──cable──▶  iPhone (Developer Mode on)
  expo run:ios --device --configuration Release
     prebuild → pod install → xcodebuild → install
  Release = JS bundle embedded → phone runs with the Mac unplugged

Analogy: a visitor badge instead of a staff badge — valid, but only for your building and only for a week. Where it breaks: TestFlight/App Store needs the paid programme; this plan never goes there.

3. Source vs prebuilt native modules (why Xcode 26.3 is a question)

Expo SDK 57 ships pre-compiled iOS frameworks built with Xcode 26.4. A Swift framework compiled by a newer compiler can't be read by an older one. This iMac (2019) can't run the macOS that Xcode 26.4 needs. But: the installed tooling only uses those prebuilt frameworks when you opt in (EXPO_USE_PRECOMPILED_MODULES=1); by default it compiles every module from source with your own Xcode. So the build should work — and Phase 0 proves it on the simulator before your phone is involved.

default          : compile expo-* from source with Xcode 26.3   ← what we do
=1 (opt-in)      : link frameworks compiled by Xcode 26.4       ← would break
fallback (O3)    : SDK 55 copy outside the repo, only if Phase 0 fails

4. Why a stopped car going quiet is fine: distanceInterval and the moving/stationary split

On iOS the harness asks for a fix every 10 m (timeInterval is Android-only). At a red light nothing moves, so nothing arrives — a 40-second silence that is correct, not a failure. analyze.mjs tags each gap MOVING or STATIONARY (haversine ≥ 15 m or speed ≥ 1.5 m/s between the bounding fixes) and only gates the moving ones.

fix ─1s─ fix ─1s─ fix ────── 40 s at a light ────── fix ─1s─ fix
                              └─ STATIONARY: reported, not gated
fix ─1s─ fix ────── 90 s while moving ────── fix
                    └─ MOVING: gated → INCONCLUSIVE (60–120 s zone)

5. The verdict, scoped honestly

The table has deliberate grey zones. PASS needs moving-gap median ≤ 5 s, p95 ≤ 15 s, p99 ≤ 30 s, none over 60 s, battery ≤ 8 %/hr. FAIL is any moving gap over 120 s, sustained batching, or battery over 12 %/hr. Between those the script prints INCONCLUSIVE and a human decides. This run adds one more scope rule: the verdict line says iOS measured, Android not, and Android defaults to the mounted-phone pattern until an Android drive passes (Q1 in the plan — say if you want #4 kept open instead).
