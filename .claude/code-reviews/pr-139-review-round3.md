### Medium

**F36 · F31 is not closed: `start_stream` keeps its own `catch`, so the most likely throw in the go-online chain still produces the exact ghost F31 was opened to kill.** `apps/driver/src/features/availability/use-presence.tsx:143-149` — `try { await startStreaming(tRef.current) } catch { dispatch({ type: 'error', code: 'generic' }) }`. That never reaches `onThrow`, so `effect_failed` never fires; `error/generic` clears `busy` and sets a banner but leaves `intent: 'online'` and `streaming: true`, and the case returns `undefined`, so the chain carries on to `connect_socket` and `keep_awake on`.

Trace (`observed` in source): Android, driver denies *background* location → `permission` with `background_denied` goes online anyway with `streaming: true` (`presence-state.ts:239-249`, deliberate — a mounted phone streams) → `put_status online` succeeds, so the server now holds the driver → `startLocationUpdatesAsync` rejects → `error/generic`. Result: toggle reads ON, socket connected, keep-awake on, **no location task**. Because no fix is ever produced, no `not_online` ack ever arrives, so the app's own re-assert safety net never fires; the driver sits on Dina's board with no stream until the dark sweep flips them at 60–75 s and pushes an "you went offline" nudge. The same trace also destroys the guidance banner (F42): «grant background location» is replaced by «something went wrong». The defect does not depend on that specific trigger — *any* `startStreaming` rejection produces it.

**Fix — delete the try/catch at `:144-148`** and let `startStreaming` reject into `runEffects`. That buys both halves at once: `onThrow` → `effect_failed` → fold + teardown, *and* `runEffects` returns, ending the chain. Do **not** merely change the code to `effect_failed`: the case returns `undefined`, so the outer chain would continue while the nested teardown runs — F32's race reopened. One test: a rejecting `startStreaming` must leave `intent: 'offline'` with no socket.

**F37 · F31's own "cannot loop" guarantee is false, and the loop it rules out is an unbounded retry on the driver's phone.** `apps/driver/src/features/availability/presence-state.ts:328` asserts *"With everything already down this is a no-op, so a throw inside the teardown below cannot loop."* `anythingUp` (`:329-332`) reads `intent || streaming || server === 'online'`, and the folded state (`:334-341`) resets `intent`, `streaming`, `busy` and `reasserted` — but **not `server`**. So the guarantee holds only for `server !== 'online'`, which is exactly the case where `effects` is `[]` and there is nothing to throw. In the case that emits effects, it does not hold.

Reachability, both conditions needed: `effect_failed` with `server === 'online'` emits `[put_status offline, ...TEAR_DOWN]`; the put fails on a dead network — **caught** at `use-presence.tsx:127-131`, dispatches `error/generic`, which touches neither `server` nor the chain, and returns `undefined` because `effect.status !== 'online'`, so the chain continues; `stop_stream` cannot throw (`.catch(() => undefined)`, `:151`); but `disconnect_socket` (`:169`, bare `teardownSocket()`, which re-throws identically each pass if it fails before `socketRef.current = null` at `:102`) and `keep_awake off` (`:172`, bare `await deactivateKeepAwake(...)` — expo-keep-awake documents an Android throw when the original Activity is dead) are **not** wrapped. Either re-enters `onThrow` → `effect_failed` → `server` still `'online'` → identical list. Termination depends on the network recovering, not on the reducer. Each pass awaits an 8 s client timeout, so it is not a CPU spin — it is a continuous retry loop against the network and the keep-awake API, i.e. battery drain, which is the one thing this product's drivers care most about.

The test agrees: `presence-state.test.ts:311-315` re-feeds `folded.state`, whose `server` is `null`; the `held` state built at `:297-300` with `server: 'online'` is never re-fed. **Fix (one line):** add `server: null` to the folded state at `:334-341`, so the second pass computes `anythingUp === false` and the docblock becomes true unconditionally. Add the missing assertion: re-feeding the `held` result must give `effects: []`. (Wrapping the two bare teardown effects the way `stop_stream` already is would also work, and is worth doing regardless.)

**F38 · The last remaining `driver_on_ride` route still tears the stream down: a driver who taps OFF mid-ride loses the ride's position feed, and #11's release then triggers a spurious nudge.** `presence-state.ts:302-306` (`drained` → `[{put_status offline}, ...TEAR_DOWN]` — the teardown is committed *before* the answer), `:310-315` (`error/driver_on_ride` → `flipOffline`), `use-presence.tsx:139-142` (F32's stop fires only for `effect.status === 'online'`, so a refused *offline* put lets the chain continue). Server: row `on_ride`, Redis presence intact; phone: not streaming. The tracking page (#63) and the board freeze on the last position, which `findNearby`'s read-time filter drops after 60 s, and the dark sweep cannot help — `markOfflineByServer` returns at `if (status !== 'online')` for an `on_ride` row. `flipOffline` also writes `server: 'offline'`, which is false. Bounded and recoverable — one tap back ON is now a 200 (F3's own fix) and `GO_ONLINE` restarts the stream (`observed` effect order: `purge_stale_fixes, put_status, start_stream, connect_socket, keep_awake`). **Not a failed closure:** round 2 offered two halves, scoped the api one to "one condition + one spec" and explicitly left the reducer's rule intact, and the author followed that. The narrow patch is to extend F32's stop to a refused offline put **only when the code is `driver_on_ride`**; a blanket stop would break the ordinary offline-with-network-error path, where teardown is correct.
