# Realtime events (reference)

**Source of truth: `RT` + payload schemas in `packages/shared/src/realtime-events.ts`.** Socket.IO, Redis adapter. Event names follow `domain:action`. Payloads are zod schemas; wire timestamps are ISO strings (`z.string().datetime()`), not `Date` — **all 9 events, no exception**. Where a wire schema is derived from a domain schema (`ride:offer`), it overrides the date fields to keep that true, because `z.coerce.date()` would make the handler's declared type a `Date` the wire never delivers.

| Event | Direction | Payload | Notes |
|---|---|---|---|
| `driver:location` | driver app → api (ping); api → dispatch room (event) | `DriverLocationPing` (in) / `DriverLocationEvent` (out) | Two schemas — see below. Throttled by TIME on the phone (≥4 s apart, `apps/driver` `fix-throttle.ts`; `distanceInterval: 0`, so a parked driver keeps pinging — the stream is the heartbeat the dark sweep reads, #14); live positions in Redis GEO, not Postgres. Inbound handler: `features/drivers/location/driver-location.gateway.ts` — identity from the JWT, and **the server stamps `at`, ignoring the client's**. A position is only recorded for a driver in the Redis online set, and is dropped from `findNearby` once older than `DRIVER_LOCATION_TTL_SECONDS` (a read-time filter, not a key TTL). Fan-out is the dispatch room only; the rider-during-active-ride leg is still future work (`driver-location.service.ts:61-62`). **The api acks each ping** with `DriverLocationAck` (`accepted`, `reason: not_online \| malformed \| store_unavailable`) — the driver app keeps every fix in a local sqlite queue and deletes it ONLY on `accepted: true` (#14); `not_online` makes the app re-assert `PUT /drivers/me/status online` once, then flip its toggle. The one acknowledgement in the catalog — a callback parameter, not an event. A driver `online` with no accepted fix for `PRESENCE_DARK_AFTER_SECONDS` (60 s) is marked offline by `DriverPresenceSweeper` (drivers slice, 15 s cadence — worst case 75 s, `derived` 60 + 15) and nudged by push 30 s later unless back online (#14) |
| `driver:queue` | api → driver app | `DriverQueueEvent` | Live place in a geozone queue; `position` is 1-based. Typed and **never emitted yet** — the queue view is #15's, beside the offer card the position belongs next to (#14 deferred it there; `features/dispatch/index.ts` KNOWN GAPS) |
| `ride:status` | api → ride room (rider + driver — **not** dispatch: `canJoin` returns false for ride rooms for every role; membership is server-orchestrated) | `RideStatusEvent` | Emitted on every state-machine transition — which is why there is no separate `ride:requested`. First emitted by `features/rides` on creation (`previousStatus: null`); #11 emits it on every subsequent transition. **`status` can move BACKWARD**: #19's dispatcher release emits `accepted\|arriving → requested`, so a consumer that treats the lifecycle as monotonic (ratchets a progress bar, refuses a "lower" status) will be wrong on that event — compare `previousStatus`, do not assume it precedes `status`. `reason` is null on the release: the dispatcher's free text is audit-only and this room contains the rider. The board deliberately doesn't need it — `dispatch:board` full frames carry ride status |
| `ride:offer` | api → driver app | `RideOfferEvent` | `rideOfferSchema.extend({...})` with ISO-string `sentAt`/`expiresAt` — one source of truth, wire-accurate timestamps. Carries `quote` **and** `split`, so the driver sees the full fare and the commission line. `rideOfferSchema.parse(payload)` re-hydrates to `Date`. Decline/timeout triggers re-offer |
| `ride:offer_revoked` | api → driver app | `RideOfferRevokedEvent` | Clears the offer card: `expired`, `taken`, or `cancelled` |
| `ride:assigned` | api → ride room + winning driver | `RideAssignedEvent` | Carries `source` and, for dispatcher overrides, `dispatcherId` |
| `dispatch:board` | api → dispatch portal | `DispatchBoardEvent` | One FULL frame of Dina's board (live rides + online drivers with name/phone/zone + every configured zone's queue + each ride's cascade state), emitted on a 2 s cadence by `features/dispatch/board/board.service.ts` (#18, extended by #19) — skipped while the local dispatch room is empty. `zones[]` is the geozone CATALOG joined to `DispatchQueueStore.snapshot()`, so empty ranks appear too; `rides[].cascade` carries the holder, deadline, next driver and the `explainAssignment()` key. Same payload as `GET /dispatch/board`; the client replaces state wholesale, and the cadence doubles as the staleness heartbeat |
| `dispatch:unclaimed` | api → dispatch portal | `DispatchUnclaimedEvent` | Flash alert for an order nobody took (S9-4). THREE triggers, only one of them time-based: past `unclaimedAlertSeconds` (`dispatch.sweeper.ts`), at `MAX_OFFER_ATTEMPTS` (`dispatch.service.ts:66`), or immediately when no candidate is eligible (`:112`) — the last fires ~1 s after booking with zero drivers online, so "past the threshold" alone is wrong. Event-driven off the 1 s sweeper — never cadence-bound |
| `dispatch:sms_failed` | api → dispatch portal | `DispatchSmsFailedEvent` | A rider SMS the platform owed was not delivered (`ride-notifications.service.ts` failure site, #18) — so Dina can phone the rider instead. Carries the SMS `kind` |

Accept/decline are **not** socket events — they are REST calls (#10), which need idempotency, auth and retry semantics. The catalog carries offer delivery and revocation only. The ack on `driver:location` is the one acknowledgement in the catalog: a callback parameter on `ClientToServerEvents`/`ClientToServerEmitEvents`, not an `RT` entry — the 9-event catalog test stays as it is.

Rules:
- Rooms: `ride:<id>` (rider+driver, joined server-side only), `dispatch:<cityId>` (board — dispatcher/admin roles), `driver:<id>` (offers), `user:<userId>` (every authenticated socket's private room — how the server addresses one person's sockets cluster-wide).
- Build room names with the `rideRoom()` / `driverRoom()` / `dispatchRoom()` / `userRoom()` helpers in `@taxi/shared` — never hand-build the strings.
- `driver:location` has **two** schemas on purpose. The inbound ping carries **no `driverId`**: the server takes the driver identity from the JWT. If the inbound schema carried it, any authenticated driver could spoof another driver's position on the dispatch board. Do not merge them.
- Socket.IO generics come from `ClientToServerEvents` / `ServerToClientEvents` in the same file. The server's listen map types inbound payloads as **`unknown`** on purpose — raw client JSON is untrusted, so the only way to read a field is `driverLocationPingSchema.parse(payload)`. The driver app emits through the typed `ClientToServerEmitEvents`.
- JWT is verified in a Socket.IO handshake middleware — an unauthenticated connection is refused before any handler runs. There is **no client-initiated join API**: the gateway places each socket in the rooms `canJoin()` allows for its role, and ride rooms are joined server-side via `RealtimeService.joinRideRoom()`.
- `@SubscribeMessage` handlers live in the **owning feature slice**, on an options-less `@WebSocketGateway()` that shares the realtime slice's authenticated server — never a second server, never a second `afterInit`, never gateway options. Subscribing to a message is not joining a room, so the no-client-join rule above is untouched.
- `RT_EVENT_SCHEMAS` (shared) maps every event to its payload schema; the api's emit helpers `.parse()` before sending, so the ISO-string rule is enforced, not just documented.
- Add an event = add it to `RT` + payload schema in shared FIRST, then this table.
